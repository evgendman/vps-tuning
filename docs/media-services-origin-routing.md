# Media Station X, Lampa, TorrServer и Jellyfin: маршрутизация, Origin и CORS

**Статус:** архитектурная спецификация для последующего развёртывания на Дубле.  
**Основание:** проверка активной конфигурации Nginx старого VPS 2026-11-19 и уточнения владельца инфраструктуры 2026-11-20.  
**Важно:** документ описывает логику и требования к будущей конфигурации. Он не означает, что перечисленные приложения или маршруты уже установлены на Дубле.

Документ дополняет [публикацию домашних сервисов через HTTPS](vps-media-services-https.md). Первый документ описывает публикацию домашних приложений через WireGuard; этот документ фиксирует отдельную локальную интеграцию Lampa, MSX, TorrServer и Jellyfin на самом VPS.

В примерах используются безопасные обозначения `<PUBLIC_HOST>`, `<LAMPA_HTTP_PORT>`, `<LAMPA_HTTPS_PORT>`, `<MSX_HTTP_PORT>`, `<MSX_HTTPS_PORT>`. Фактические домен, публичный IP, пароли, токены и индивидуальные ссылки в документ не включаются.

## 1. Цели архитектуры

При переносе на Дубль важно сохранить не отдельные старые Nginx-файлы, а следующие свойства:

1. Media Station X (MSX) должна запускаться на телевизорах как по HTTP, так и по HTTPS: разные модели телевизоров и версии MSX предъявляют разные требования к стартовому URL.
2. Через MSX пользователь должен иметь возможность открыть Lampa или Jellyfin.
3. Lampa, её JavaScript-плагины и локальный TorrServer должны взаимодействовать через один Origin, чтобы встроенные браузеры телевизоров не сталкивались с проблемами междоменных запросов и авторизации.
4. Плагины Lampa должны загружаться без Basic Auth.
5. Для интеграции Lampa с TorrServer не требуется открывать полноценный административный интерфейс TorrServer. Публикуется отдельный ограниченный по назначению proxy path; фактическое поведение API и доступных операций определяется также реализацией TorrServer.
6. Jellyfin должен иметь два логически разных способа использования:
   - собственный веб-интерфейс и API с авторизацией самого Jellyfin;
   - специальный публичный URL-путь `/Videos/` для воспроизведения по заранее сформированным длинным ссылкам во внешних плеерах, без дополнительного Basic Auth Nginx.
7. CORS включается только там, где он действительно требуется. Он не должен дублировать заголовки, уже возвращаемые upstream-приложением.

## 2. Термины: Origin и CORS

### 2.1. Что считается одним Origin

Origin определяется сочетанием схемы, доменного имени и порта:

- `https://<PUBLIC_HOST>:<LAMPA_HTTPS_PORT>/`;
- `https://<PUBLIC_HOST>:<LAMPA_HTTPS_PORT>/plugins/example.js`;
- `https://<PUBLIC_HOST>:<LAMPA_HTTPS_PORT>/torrserver/torrents`

— один и тот же Origin: путь не участвует в его определении.

Но другой порт или другая схема создают другой Origin. Поэтому HTTP и HTTPS, а также два HTTPS-порта одного домена — разные Origin.

### 2.2. Роль reverse proxy

Когда Lampa обращается к `/torrserver/...` на том же протоколе, домене и порту, браузер видит запрос к тому же Origin. Nginx внутри сервера проксирует запрос на локальный TorrServer, но внутренний адрес upstream браузеру не виден.

Это основной механизм совместимости Lampa с TorrServer. В этом сценарии CORS для запроса Lampa → `/torrserver/` не нужен: запрос same-origin.

### 2.3. Что CORS делает и чего не делает

CORS — политика браузера, регулирующая, может ли JavaScript прочитать ответ ресурса, расположенного на другом Origin. Это не firewall, не аутентификация и не универсальная защита API.

Нужно различать два разных случая:

- **Загрузка JS-файла плагина.** Заголовки CORS на URL `/plugins/*.js` могут понадобиться, когда скрипт загружается с другого Origin, в частности при использовании CORS-режима загрузки или ES modules. Для обычного same-origin подключения они обычно не нужны.
- **Запросы, выполняемые самим плагином.** Если код плагина вызывает `fetch` или `XMLHttpRequest` к API на другом Origin, разрешающий CORS-заголовок должен вернуть именно сервер этого API (или reverse proxy, через который идёт запрос). Наличие CORS на URL JS-файла само по себе не разрешает плагину обращаться к другим API.

Поэтому CORS на Lampa plugin path и CORS на TorrServer API path решают разные задачи. При использовании same-origin proxy path второй набор заголовков для Lampa не нужен, но CORS на API может понадобиться другим внешним клиентам.

### 2.4. Запросы с credentials

Ответ с `Access-Control-Allow-Origin: *` не подходит для credentialed CORS-запросов, в которых браузер отправляет credentials, например cookies или HTTP-аутентификацию через `fetch(..., { credentials: "include" })`.

Для такого режима сервер должен возвращать конкретный разрешённый Origin и `Access-Control-Allow-Credentials: true`. Нельзя просто сочетать wildcard `*` с credentialed CORS.

Для интеграций, где используются cookies или Basic Auth, допустимые Origin, методы, заголовки и режим credentials необходимо определить отдельно. Не следует включать credentials «на всякий случай».

## 3. Media Station X: две точки входа

MSX — самостоятельное приложение для телевизоров. Его стартовый файл `start.json` сообщает MSX, какое приложение или меню открыть и где получить следующую конфигурацию.

Некоторые телевизоры и версии MSX принимают HTTP URL, другие требуют HTTPS. Поэтому на VPS должны быть доступны два варианта стартового URL — HTTP и HTTPS. Это не следует сводить к одному HTTPS-редиректу: HTTP-вариант нужен именно тем клиентам, которые не могут использовать HTTPS.

### 3.1. Каталоги и назначение файлов

На старом VPS обнаружены два разных дерева:

| Каталог | Назначение |
|---|---|
| `/var/www/msx/` | Стартовые и меню-файлы MSX для Jellyfin |
| `/var/www/lampa/msx/` | MSX-файлы, относящиеся к самой Lampa |

В `/var/www/msx/` находятся:

- `start.json` — входная конфигурация MSX для Jellyfin;
- `menu.json` — меню с переходом к веб-интерфейсу Jellyfin.

В `/var/www/lampa/msx/` находится собственный `start.json` Lampa. Это отдельный файл и его нельзя подменять стартовым файлом Jellyfin.

### 3.2. Требования к будущей конфигурации

- Опубликовать HTTP и HTTPS стартовые адреса, пригодные для разных моделей ТВ/MSX.
- Сохранить корректные `root` или `alias` для соответствующего дерева файлов.
- Не требовать Basic Auth для публичных файлов, которые MSX должен получить до открытия самого приложения.
- Убедиться, что относительные и абсолютные ссылки внутри JSON ведут на правильный публичный адрес и нужный порт.
- Проверить прохождение всей цепочки: старт MSX → загрузка `start.json` → загрузка `menu.json` или следующего ресурса → запуск Lampa/Jellyfin.
- Не путать стартовый каталог MSX с корнем веб-сайта Lampa и не смешивать их файлы.

На старом VPS файлы из `/var/www/msx/` обслуживались через `/msx/` несколькими виртуальными серверами, в том числе HTTP и HTTPS. Точный набор портов на Дубле следует спроектировать с учётом выбранных публичных URL и сертификата; механически копировать старые порты не требуется.

## 4. Lampa: интерфейс, плагины и TorrServer в одном Origin

### 4.1. Интерфейс Lampa

Корневой путь Lampa (`/`) защищается Basic Auth Nginx. Это защита входа в интерфейс, а не обязательное требование ко всем URL того же virtual host.

На старом VPS использовались отдельные HTTP и HTTPS virtual hosts Lampa. При переносе порты следует выбрать для Дубля отдельно.

### 4.2. Плагины Lampa

Путь `/plugins/` обслуживает статические JavaScript-файлы из каталога Lampa, например `/var/www/lampa/plugins/`.

Требования:

- не требовать Basic Auth на `/plugins/`, иначе телевизор/встроенный браузер может не загрузить плагин;
- указывать правильный физический каталог через `root` или `alias`;
- сохранять необходимые MIME-типы для JavaScript;
- при подтверждённой междоменной загрузке скриптов возвращать подходящие CORS-заголовки;
- не считать CORS на JS-файлах заменой CORS на API, к которым обращается код плагина.

На старом VPS для plugin path задавались `Access-Control-Allow-Origin: *`, методы `GET, POST, OPTIONS` и JavaScript Content-Type. При переносе эти заголовки следует сохранить только в объёме, подтверждённом фактическим способом загрузки плагинов. Для same-origin загрузки wildcard CORS не является обязательным.

### 4.3. Локальный TorrServer через дополнительный путь Lampa

Lampa использует настройку URL TorrServer. Чтобы не задавать в Lampa отдельные логин и пароль TorrServer и не создавать второй Origin, в URL TorrServer задаётся путь на том же публичном Origin Lampa.

Концептуальный URL:

`https://<PUBLIC_HOST>:<LAMPA_HTTPS_PORT>/torrserver`

Вызов API, например, становится:

`https://<PUBLIC_HOST>:<LAMPA_HTTPS_PORT>/torrserver/torrents`

Браузер видит тот же Origin, что и у Lampa. Nginx принимает запрос на дополнительном пути и передаёт его локальному TorrServer на VPS.

На старом VPS локальный upstream TorrServer работал на loopback-порту 8094. На Дубле этот порт является планируемым значением, а не уже проверенным фактом: при установке нужно сверить фактический listener и конфигурацию TorrServer.

### 4.4. Переписывание URI

На старом VPS использовалась логика:

```nginx
location /torrserver/ {
    rewrite ^/torrserver/(?:gst/)?(.*)$ /$1 break;
    proxy_pass http://127.0.0.1:8094;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_buffering off;
}
```

Назначение rewrite — удалить внешний служебный префикс и, если он присутствует, дополнительный сегмент `gst/`, чтобы upstream получил ожидаемый TorrServer URI.

Примеры:

| URI от браузера | URI после rewrite для upstream |
|---|---|
| `/torrserver/torrents` | `/torrents` |
| `/torrserver/gst/stream` | `/stream` |
| `/torrserver/gst/<path>` | `/<path>` |

Это важно не только для API-запроса `/torrents`, но и для формирования/обработки ссылок воспроизведения. При переносе rewrite нельзя удалять или упрощать без проверки всех используемых TorrServer URL.

Маршрут нужен для конкретной интеграции Lampa. Он не должен автоматически превращаться в публикацию полного интерфейса TorrServer. Однако отсутствие Basic Auth на Nginx не следует считать самостоятельной защитой API: необходимо сохранять и проверять реальное поведение TorrServer, его доступные endpoints и ограничения.

### 4.5. CORS на TorrServer proxy path

В старой конфигурации Nginx добавлял собственные CORS-заголовки и обрабатывал OPTIONS. При этом сам TorrServer на loopback также возвращал CORS-заголовки. Проверка OPTIONS через Nginx показала дублирующийся `Access-Control-Allow-Origin: *`.

Такую избыточность переносить нельзя: повторяющиеся CORS-заголовки могут приводить к отказу браузера принять ответ.

Рекомендуемый порядок:

1. Для Lampa использовать same-origin путь `/torrserver/`; CORS на этом взаимодействии не требуется.
2. Для клиентов, действительно обращающихся к TorrServer с другого Origin, определить, кто единственный владелец CORS-политики — TorrServer или Nginx.
3. Не добавлять второй `Access-Control-Allow-Origin`, если его уже возвращает upstream.
4. Проверять OPTIONS/preflight и фактический GET/POST/XHR из браузера, а не только наличие директив в конфиге.

## 5. Jellyfin и специальный путь /Videos/ для внешних плееров

На старом VPS существуют два независимых способа обратиться к Jellyfin:

1. Jellyfin, установленный непосредственно на VPS, с локальным upstream `127.0.0.1:8096`.
2. Домашний Jellyfin, доступный через WireGuard/маршрутизатор по отдельному публичному сервисному маршруту. Его публикация описана в [vps-media-services-https.md](vps-media-services-https.md).

Их нельзя смешивать: одинаковый порт приложения не означает один и тот же сервер.

### 5.1. Собственный интерфейс Jellyfin

Корневой маршрут локального Jellyfin проксируется на `127.0.0.1:8096` без дополнительного Basic Auth Nginx. Пользователей аутентифицирует сам Jellyfin.

Это также относится к публикации домашнего Jellyfin на отдельном сервисном порту: дополнительный Basic Auth Nginx не используется, поскольку приложение имеет собственную авторизацию.

### 5.2. Путь /Videos/

На старом VPS путь `/Videos/` был отдельным публичным маршрутом к локальному Jellyfin:

```nginx
location ^~ /Videos/ {
    proxy_pass http://127.0.0.1:8096;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;

    proxy_buffering off;
    proxy_request_buffering off;

    auth_basic off;

    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
    send_timeout 3600s;
}
```

Назначение — воспроизведение по уже готовым длинным ссылкам из внешних плееров (например, Stremio или другого клиента), а не предоставление полноценного веб-интерфейса Jellyfin.

Требования при возможном восстановлении на Дубле:

- не включать Basic Auth Nginx на `/Videos/`, иначе внешние плееры не смогут использовать готовые ссылки ожидаемым способом;
- проксировать URI и query string без непреднамеренного изменения;
- сохранять поддержку потоковой передачи и Range-запросов;
- не включать буферизацию ответа Nginx;
- проверить поведение URL, токенов/ключей доступа и редиректов на фактических клиентах;
- не добавлять CORS без подтверждения, что клиент обращается через Fetch/XHR или MSE с другого Origin и требует preflight.

Длинная медиассылка может содержать токен или другой секрет авторизации Jellyfin. Такие ссылки нельзя включать в публичную документацию, журналы примеров или GitHub issue. Отсутствие Basic Auth Nginx не означает, что сам Jellyfin или медиаресурс обязательно доступны без токена.

На момент анализа upstream `127.0.0.1:8096` был штатным адресом установленного Jellyfin на старом VPS, но сервис был временно остановлен после проблемы с заполнением диска. Поэтому полученный тогда HTTP 502 был следствием недоступности upstream, а не доказательством ошибочного назначения маршрута.

Путь `/Videos/` сейчас не является обязательной частью первоначального развёртывания Дубля. Его следует добавлять, когда появится конкретный внешний плеер и будет проверен формат его готовых ссылок.

## 6. Basic Auth: исключения должны задаваться на уровне конкретных путей

На старом VPS авторизация была настроена не одинаково для всего virtual host. В некоторых конфигурациях `auth_basic` задан непосредственно внутри `location /`, а соседние пути имеют собственное поведение.

Проверенная логика старой конфигурации:

| Сервис / путь | Поведение Nginx Basic Auth | Назначение |
|---|---|---|
| Lampa `/` | Включена | Защита интерфейса Lampa |
| Lampa `/plugins/` | Явно отключена | Загрузка JS-плагинов |
| Lampa `/torrserver/` | Не применяется | Интеграционный proxy path к локальному TorrServer |
| Lampa `/msx/` | Попадает под защиту корневого маршрута | Файлы из дерева Lampa, не публичный MSX Jellyfin |
| Jellyfin `/` | Не применяется | Собственная авторизация Jellyfin |
| Jellyfin `/msx/` | Явно отключена | Публичные файлы MSX |
| TorrServer UI `/` | Включена | Защита интерфейса TorrServer |
| TorrServer `/Videos/` | Явно отключена | Готовые медиассылки внешних плееров |
| TorrServer `/msx/` | Явно отключена | Файлы MSX |
| TorrServer `/plugins/` на HTTP | Явно отключена | Публичные статические плагины |
| TorrServer `/.well-known/acme-challenge/` | Явно отключена | ACME HTTP-01 |

Basic Auth наследуется от вышестоящего уровня конфигурации Nginx, пока не переопределён в выбранном `location`. Директива, заданная внутри одного `location`, не означает, что соседний `location` автоматически защищён тем же способом.

При проектировании каждого нового virtual host нужно явно определить политику для всех путей. Нельзя считать, что защита корневого URL автоматически означает защиту всех API и каталогов, и наоборот.

Публичные интеграционные маршруты следует открывать только в требуемом объёме. Не следует отключать Basic Auth для всего virtual host только ради одного публичного каталога или proxy path.

## 7. Различия старой HTTP- и HTTPS-конфигурации, которые не нужно копировать вслепую

Проверка старого VPS выявила некоторые исторические расхождения:

- На HTTP TorrServer path `/plugins/` обслуживал `/var/www/html/plugins/`.
- В HTTPS virtual host TorrServer для `/plugins/` было только `auth_basic off`, но не было `root` или `alias`; фактический URL возвращал 404.
- MSX tree `/var/www/msx/` обслуживался через несколько virtual hosts, включая HTTP и HTTPS.
- `/Videos/` был настроен в HTTP и HTTPS virtual hosts TorrServer, но использовал один и тот же локальный Jellyfin upstream.
- Для CORS на TorrServer proxy path получалось дублирование заголовков от Nginx и самого TorrServer.

При создании конфигурации Дубля необходимо переносить назначение и проверенное поведение, а не исторические ошибки, неиспользуемые копии и лишние директивы.

## 8. Разделение локальных и домашних сервисов Дубля

Для будущего развёртывания необходимо явно различать локальные upstream-процессы VPS и сервисы домашнего MINI-Ubuntu.

| Компонент | Где расположен | Как должен использоваться |
|---|---|---|
| Lampa | Планируется на VPS | Собственный virtual host |
| Локальный TorrServer для Lampa | Планируется на VPS | Loopback upstream; целевой порт сверить после установки |
| `/torrserver/` | Nginx на VPS | Прокси к локальному TorrServer с rewrite |
| Локальный Jellyfin для `/Videos/` | Был установлен на старом VPS; на Дубле не является обязательным | Loopback upstream при необходимости внешних плееров |
| Домашний Jellyfin | MINI-Ubuntu через WireGuard и Keenetic | Отдельный публичный сервисный маршрут |
| Домашний TorrServer | MINI-Ubuntu через WireGuard и Keenetic | Отдельный публичный сервисный маршрут |

На старом VPS Lampa использовала TorrServer, установленный на том же VPS, поэтому upstream был loopback `127.0.0.1:8094`. На Дубле также планируется локальная установка TorrServer, но фактический порт и режим запуска нужно сверить после установки.

Домашние сервисные порты, которые Nginx публикует через WireGuard (например, публичный маршрут домашнего TorrServer), не являются заменой локального TorrServer, используемого Lampa через same-origin path.

## 9. Что переносить и в какой последовательности

### Этап 1. Базовая Lampa и локальный TorrServer

- [ ] Установить Lampa и локальный TorrServer на Дубль.
- [ ] Проверить, на каких loopback-портах реально слушают приложения.
- [ ] Создать HTTP/HTTPS virtual hosts Lampa согласно требуемым клиентским URL.
- [ ] Защитить Basic Auth интерфейс Lampa, но оставить `/plugins/` публичным.
- [ ] Создать `/torrserver/` proxy path на том же Origin.
- [ ] Сохранить и проверить rewrite для обычных и `gst/` путей.
- [ ] Настроить URL TorrServer в Lampa на локальный proxy path, а не на отдельный публичный порт.
- [ ] Не задавать в Lampa отдельные credentials TorrServer, если выбранная схема обходится без них.
- [ ] Проверить загрузку плагина, вызов API списка TorrServer, добавление/удаление и воспроизведение.

### Этап 2. Media Station X

- [ ] Определить HTTP и HTTPS стартовые URL для MSX на Дубле.
- [ ] Разместить раздельные стартовые конфигурации и меню для Lampa и Jellyfin.
- [ ] Опубликовать только необходимые JSON-файлы без Basic Auth.
- [ ] Проверить правильность ссылок, которые MSX получает из `start.json` и `menu.json`.
- [ ] Проверить запуск и навигацию на фактических телевизорах/версиях MSX, поддерживающих HTTP и HTTPS соответственно.

### Этап 3. Jellyfin и внешние плееры

- [ ] Установить или запустить локальный Jellyfin, если он нужен на Дубле.
- [ ] Сохранить собственную авторизацию Jellyfin, не добавляя Basic Auth Nginx перед его UI.
- [ ] При появлении требования внешнего плеера создать `/Videos/` с публичным для Nginx доступом.
- [ ] Проверить готовые ссылки, Range/seek, длительную передачу, query string, авторизационные токены и редиректы.
- [ ] Решить вопрос CORS по фактическому механизму плеера, а не добавлять wildcard автоматически.

### Этап 4. Приёмочная проверка и фиксация

- [ ] Проверить конфигурацию `nginx -t` перед reload.
- [ ] Проверить HTTP и HTTPS стартовые URL MSX без Basic Auth.
- [ ] Проверить, что защищённый интерфейс Lampa возвращает HTTP 401 без учётных данных.
- [ ] Проверить, что `/plugins/` возвращает JS-файлы без HTTP 401.
- [ ] Проверить, что Lampa → `/torrserver/` остаётся same-origin.
- [ ] Проверить OPTIONS только для тех междоменных API, где он действительно нужен.
- [ ] Убедиться, что в ответе нет дублирующихся `Access-Control-Allow-Origin`.
- [ ] Проверить реальные телевизоры и плееры, а не только ответы `curl`.
- [ ] Сохранить итоговую безопасную архитектуру и таблицу маршрутов в документации.

## 10. Правила CORS при реализации

1. Не добавлять `Access-Control-Allow-Origin: *` глобально на весь Nginx.
2. Не дублировать CORS-заголовки upstream-приложения на уровне Nginx.
3. Не считать CORS на URL JS-плагина разрешением его последующим API-запросам.
4. Предпочитать same-origin reverse proxy там, где он решает задачу без междоменных запросов.
5. Для публичных JSON/JS ресурсов MSX и Lampa включать CORS только для реально используемых cross-origin сценариев.
6. Для credentialed CORS указывать конкретные доверенные Origin и `Access-Control-Allow-Credentials: true`; wildcard не использовать.
7. Для preflight проверять реальные `Access-Control-Request-Method` и `Access-Control-Request-Headers`, а не разрешать произвольные методы и заголовки без необходимости.
8. Отсутствие Basic Auth в Nginx не является заменой проверке собственной авторизации и границ доступа upstream-приложения.

## 11. Область, которую пока не переносим

Публичный маршрут Transmission на отдельном порту старого VPS (`8290`) не входит в текущий план переноса. Если он понадобится, его следует спроектировать заново с учётом актуального приложения, способа авторизации и сетевого расположения upstream.

Маршрут `/Videos/` также не обязателен для первоначального этапа Дубля: он восстанавливается при появлении реального сценария использования внешнего плеера.

## 12. Публичная документация и секреты

В репозитории допустимо хранить архитектуру, роли сервисов, общие порты, пути к конфигурационным файлам, безопасные шаблоны Nginx и методику тестирования.

Не включать:

- реальный публичный IP и настоящее имя сайта;
- пароли, содержимое `.htpasswd`, API-ключи и токены;
- реальные длинные медиассылки с токенами;
- клиентские настройки Lampa с сохранёнными credentials;
- конфигурации WireGuard и приватные ключи;
- реальные резервные копии конфигураций VPS.

Все резервные копии с секретами остаются локально на соответствующем VPS.
