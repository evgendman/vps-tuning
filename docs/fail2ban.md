# Fail2ban: защита SSH на VPS

**Статус:** Fail2ban установлен, настроен и запущен на обоих VPS. На каждом сервере служба и jail `sshd` работают независимо, со своим списком доверенных административных адресов.

## 1. Зачем нужен Fail2ban

Fail2ban анализирует события неудачной аутентификации и временно блокирует источники, которые превышают установленный порог попыток. В нашей конфигурации он предназначен только для снижения количества повторных попыток подбора пароля к SSH.

Это не замена SSH-ключам, ограничению входа привилегированных учётных записей, обновлениям ОС или сетевому firewall. Fail2ban не останавливает распределённое сканирование, при котором каждый адрес делает мало попыток, и не защищает от входа с корректными учётными данными.

## 2. Применённая политика

| Параметр | Значение | Назначение |
|---|---:|---|
| Пакет | `fail2ban 1.1.0-9` | Версия, проверенная при первом внедрении; при повторной установке сверять версию в репозитории ОС |
| Jail | `sshd` | Защищается только SSH |
| Порт и протокол | TCP/22 | Область применения блокировки |
| Backend | `systemd` | Чтение событий из systemd journal |
| `maxretry` | `8` | Число неудачных попыток до блокировки |
| `findtime` | `10m` | Окно подсчёта попыток |
| `bantime` | `1h` | Первоначальная длительность блокировки |
| Banaction | `nftables[type=multiport]` | Отдельное действие nftables с ограничением по порту |

Список `ignoreip` включает loopback и только проверенные административные источники, необходимые для конкретного сервера. Реальные адреса в публичном документе не приводятся: при восстановлении конфигурации вместо placeholders нужно подставить актуальные доверенные IP/CIDR из приватных данных данного VPS. Не добавлять широкие диапазоны провайдеров, хостингов или VPN.

## 3. Файл конфигурации

Локальный файл на каждом VPS:

`/etc/fail2ban/jail.d/zz-sshd.local`

Содержимое, с заменяемыми placeholders:

~~~ini
[DEFAULT]
ignoreip = 127.0.0.1/8 ::1 <TRUSTED_ADMIN_IP_1/CIDR> <TRUSTED_ADMIN_IP_2/CIDR>
bantime = 1h
findtime = 10m
maxretry = 8
backend = systemd
banaction = nftables[type=multiport]

[sshd]
enabled = true
filter = sshd
backend = systemd
journalmatch = _SYSTEMD_UNIT=ssh.service
port = 22
protocol = tcp
~~~

Строка `journalmatch = _SYSTEMD_UNIT=ssh.service` намеренно не ограничивает события значением `_COMM=sshd`: это позволяет учитывать также сообщения процесса `sshd-session`, используемого актуальной версией OpenSSH. При адаптации к другой ОС необходимо проверить фактические поля её SSH-журнала и работу фильтра.

`nftables[type=multiport]` — используемый синтаксис действия в установленной версии Fail2ban. Для этой политики создаётся отдельная таблица Fail2ban (по умолчанию `inet f2b-table`) и собственная цепочка. Правило ограничено TCP-портом 22. Цепочки Docker, включая `DOCKER-USER`, правила NAT, WireGuard и Nginx не должны редактироваться ради этого jail.

## 4. Как внедряли

1. До установки проверили SSH: служба была активна, порт TCP/22 слушался, существующая административная сессия сохранялась. Также проверили активный nftables ruleset, Docker-цепочки и сетевую схему каждого VPS.
2. Убедились в наличии независимого способа восстановления доступа через консоль провайдера.
3. Установили Fail2ban из штатного репозитория ОС. Автоматический запуск службы на этапе установки был временно отложен, чтобы сначала подготовить и проверить локальную конфигурацию.
4. Создали отдельный файл `zz-sshd.local` с jail `sshd`, backend `systemd`, ограничением TCP/22 и параметрами из раздела 2. В `ignoreip` внесли только доверенные административные источники соответствующего сервера.
5. Проверили конфигурацию командой `sudo fail2ban-client -t`, а работу фильтра — на выборке недавних SSH-событий из systemd journal. В частности, подтвердили распознавание сообщений `sshd-session`.
6. После проверки запустили службу и включили её автозапуск через systemd.
7. Проверили ответ `fail2ban-client ping`, состояние jail, таблицу nftables и сохранность SSH-доступа.
8. Отдельно проверили добавление тестового адреса в бан и снятие этого бана. После проверки тестовый адрес был удалён из набора блокировки.

Установка и настройка проводились отдельно на каждом VPS. Нельзя считать, что локальный файл с `ignoreip`, сетевые интерфейсы и прочие индивидуальные параметры одного VPS можно без проверки копировать на другой.

## 5. Проверка состояния

~~~bash
sudo systemctl is-active fail2ban
sudo systemctl is-enabled fail2ban
sudo fail2ban-client ping
sudo fail2ban-client status
sudo fail2ban-client status sshd
sudo journalctl -u fail2ban -n 100 --no-pager
sudo nft list table inet f2b-table
~~~

Для проверки свежих SSH-событий:

~~~bash
sudo journalctl -u ssh --since "10 minutes ago" --no-pager
~~~

Тестовое добавление и удаление адреса допустимо выполнять только с отдельным тестовым адресом, который не принадлежит административному подключению:

~~~bash
sudo fail2ban-client set sshd banip <TEST_IP>
sudo fail2ban-client set sshd unbanip <TEST_IP>
~~~

После теста убедиться, что адрес отсутствует в бане и административный доступ работает. Не проверять защиту серией реальных неудачных входов со своего текущего адреса.

## 6. Важные ограничения и безопасная эксплуатация

- Не менять SSH-порт, параметры аутентификации или правила firewall в рамках обслуживания Fail2ban без отдельного плана и проверки альтернативного доступа.
- Не включать UFW как часть этой настройки. Действующий сетевой firewall и публикация сервисов требуют отдельного аудита.
- Не запускать глобальный `nft flush ruleset`: это может удалить правила Docker и нарушить маршрутизацию.
- Не редактировать и не очищать `DOCKER-USER` ради Fail2ban. Бан должен действовать только на SSH.
- Перед добавлением адреса в `ignoreip` проверить его принадлежность и стабильность. Не переносить исключения между VPS автоматически.
- Не публиковать реальные адреса из `ignoreip`, текущий список банов, SSH-журналы, дампы firewall и приватные конфигурации.

Подробные ограничения и общая стратегия восстановления VPS описаны в [дорожной карте](roadmap.md).
