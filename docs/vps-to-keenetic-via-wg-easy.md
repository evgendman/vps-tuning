# Доступ с VPS в домашнюю сеть через WireGuard peer Keenetic

**Статус:** документирует проверенную конфигурацию VPS на 2026-10-17.  
**Цель:** из процессов на VPS обращаться к WireGuard-узлу Keenetic по адресу `10.8.0.2`, а дальнейшую маршрутизацию к устройствам домашней LAN выполнять на Keenetic.

> Документ не содержит публичных IP-адресов, приватных ключей, preshared keys или иных секретов. Значения адресов ниже — внутренние адреса используемой схемы.

## 1. Схема

Трафик проходит по цепочке:

```text
Приложение / процесс на VPS
        |
        | маршрут 10.8.0.2/32
        v
Хостовая таблица маршрутизации VPS
        |
        | via 172.17.0.3 dev docker0
        v
Docker bridge: docker0 (172.17.0.0/16)
        |
        v
Контейнер wg-easy (172.17.0.3)
        |
        | интерфейс WireGuard wg0 (10.8.0.1/24)
        v
WireGuard peer Keenetic (10.8.0.2/32)
        |
        v
Маршрутизация / правила доступа на Keenetic
        |
        v
Нужное устройство или сервис домашней LAN
```

Идея схемы в том, что интерфейс WireGuard находится внутри сетевого пространства имён контейнера `wg-easy`, а не непосредственно на хосте VPS. Поэтому на хосте установлен маршрут к peer Keenetic через IP контейнера как next hop. Контейнер получает пакет и маршрутизирует его в свою сеть WireGuard.

### Подтверждённые параметры

| Параметр | Значение |
|---|---|
| Имя контейнера | `wg-easy` |
| Docker image | `ghcr.io/wg-easy/wg-easy` |
| Docker network | `bridge` |
| Интерфейс хоста для Docker bridge | `docker0` |
| Подсеть Docker bridge | `172.17.0.0/16` |
| IP хоста на `docker0` | `172.17.0.1` |
| IP контейнера `wg-easy` | `172.17.0.3` |
| Интерфейс WireGuard внутри контейнера | `wg0` |
| Адрес WireGuard-интерфейса | `10.8.0.1/24` |
| Адрес peer Keenetic | `10.8.0.2/32` |
| Маршрут на хосте | `10.8.0.2/32 via 172.17.0.3 dev docker0` |
| Служба маршрута | `route-to-keenetic.service` |

В выводе `wg show` на контейнере для peer `10.8.0.2/32` наблюдался актуальный handshake и ненулевые счётчики переданного/полученного трафика. Это подтверждает, что peer WireGuard настроен и обменивался трафиком в момент проверки.

## 2. Постоянный маршрут через systemd

Маршрут добавляется не только вручную: он оформлен отдельной systemd-службой:

Файл: `/etc/systemd/system/route-to-keenetic.service`

```ini
[Unit]
Description=Route to Keenetic via wg-easy
After=docker.service
Requires=docker.service

[Service]
Type=oneshot
ExecStart=/usr/sbin/ip route replace 10.8.0.2/32 via 172.17.0.3 dev docker0
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
```

Служба включена в автозапуск (`systemctl is-enabled route-to-keenetic.service` возвращает `enabled`).

### Что означают директивы

- `After=docker.service` — запускает службу маршрута в порядке после запуска службы Docker.
- `Requires=docker.service` — связывает запуск с `docker.service`; при недоступности требуемой службы запуск не должен считаться штатным.
- `Type=oneshot` — выполняет одну команду и завершает процесс службы.
- `ip route replace` — создаёт маршрут или заменяет существующий; команду можно повторять без создания дубликатов.
- `RemainAfterExit=yes` — после успешного выполнения systemd показывает состояние `active (exited)`. Для такой одноразовой службы это нормальное состояние.
- `WantedBy=multi-user.target` вместе с `systemctl enable` обеспечивает запуск во время обычной загрузки системы.

Маршрут ядра сам по себе временный, но служба восстанавливает его при загрузке VPS. Фактическое наличие маршрута следует проверять командой `ip route`, а не только по статусу systemd.

### Важная тонкость о порядке запуска

Фактический unit-файл содержит `After=docker.service`, а не явную директиву `After=network-online.target`. Поэтому точное описание таково: служба маршрута запускается после службы Docker. Она **не ждёт отдельной проверки готовности контейнера `wg-easy`** и не сверяет его текущий IP перед добавлением маршрута.

В текущей рабочей конфигурации это принято, поскольку адрес контейнера `172.17.0.3` проверялся после перезагрузок и сохранялся. Если при новой установке требуется гарантированно дождаться запуска контейнера, unit можно усилить ожиданием состояния контейнера и проверкой его IP до команды `ip route replace`.

## 3. Создание службы с нуля

Этот порядок относится к этапу, когда Docker и контейнер `wg-easy` уже настроены, WireGuard работает, а контейнер имеет нужный IP.

1. Убедиться, что `wg-easy` действительно использует Docker-сеть `bridge` и адрес `172.17.0.3`. Не полагаться на предположение, что Docker всегда сам выдаст этот адрес после пересоздания контейнера.
2. Создать файл `/etc/systemd/system/route-to-keenetic.service` с содержимым из раздела 2.
3. Перечитать конфигурацию systemd и включить/запустить службу:

   ```bash
   sudo systemctl daemon-reload
   sudo systemctl enable --now route-to-keenetic.service
   ```

4. Проверить, что маршрут появился в таблице ядра и указывает на контейнер:

   ```bash
   ip -4 route get 10.8.0.2
   ip -4 route show 10.8.0.2/32
   ```

Ожидаемый маршрут:

```text
10.8.0.2 via 172.17.0.3 dev docker0
```

Если адрес контейнера или сетевой интерфейс отличается, сначала выяснить правильную топологию. Не запускать команду с прежним next hop вслепую.

## 4. Проверка и диагностика

Команды для проверки без изменения конфигурации:

### Маршрут хоста VPS

```bash
ip -4 route get 10.8.0.2
ip -4 route show 10.8.0.2/32
systemctl is-enabled route-to-keenetic.service
systemctl status route-to-keenetic.service --no-pager
journalctl -u route-to-keenetic.service -b --no-pager
```

### IP контейнера и Docker-сеть

```bash
docker ps --filter name=wg-easy
docker inspect wg-easy \
  --format '{{.Name}} {{range .NetworkSettings.Networks}}{{.NetworkID}} {{.IPAddress}} {{end}}'
docker network inspect bridge
```

### WireGuard внутри контейнера

Утилита `wg` может отсутствовать непосредственно на хосте VPS — это не доказывает неисправность туннеля. Проверять его следует внутри контейнера:

```bash
docker exec wg-easy wg show
docker exec wg-easy ip -4 route
```

Ожидается интерфейс `wg0`, маршрут сети `10.8.0.0/24` через него и peer с `AllowedIPs: 10.8.0.2/32`. Для проверки соединения дополнительно смотреть `latest handshake` и счётчики трафика.

## 5. Тонкости и типичные неисправности

### Перезагрузка VPS и пересоздание контейнера — разные события

- **Перезагрузка VPS:** текущая служба повторно устанавливает хостовый маршрут; адрес `172.17.0.3` по многократным проверкам сохранялся.
- **Удаление и создание контейнера заново:** Docker может выдать контейнеру другой адрес, если IP не закреплён конфигурацией. Тогда команда службы продолжит направлять пакеты на `172.17.0.3`, даже если `wg-easy` уже получил другой адрес.

После изменений Docker всегда сверять IP контейнера и маршрут. Если адрес должен оставаться неизменным и после пересоздания, закрепить его явно в конфигурации Docker с учётом свободных адресов выбранной сети.

### `active (exited)` не означает, что маршрут всё ещё существует

Это ожидаемый статус для `Type=oneshot` + `RemainAfterExit=yes`. Системный маршрут можно удалить отдельно, и systemd не обязательно выполнит команду повторно. Проверка истины — `ip -4 route get 10.8.0.2`.

### Рабочий handshake не гарантирует доступность каждого LAN-сервиса

Проверка peer подтверждает работу WireGuard между VPS и Keenetic, но не гарантирует, что на Keenetic настроены маршруты, правила firewall и разрешение доступа к конкретному устройству/порту домашней LAN. Эти настройки выполняются отдельно на Keenetic. В этом документе не фиксируются конкретные LAN-подсеть, правила firewall/NAT и портовые перенаправления, поскольку их значения не были частью подтверждённой конфигурации VPS.

### Если маршрут есть, но доступа нет

Проверять последовательно:

1. `ip route get 10.8.0.2` на VPS — действительно ли выбран next hop `172.17.0.3`.
2. IP контейнера и наличие контейнера в Docker-сети.
3. `wg show` внутри контейнера — актуальность handshake и движение счётчиков.
4. маршрутизацию и firewall на Keenetic до нужного адреса/порта LAN, а также обратный маршрут для ответного трафика.

Не отключать firewall и не добавлять широкие правила NAT в качестве первого диагностического действия.

## 6. Что не следует фиксировать в публичном репозитории

Не коммитить приватные и preshared WireGuard-ключи, конфиги с приватными ключами, токены, пароли и клиентские конфигурации. Публичные IP-адреса VPS и клиентов тоже не нужны для описания этой схемы — для документации достаточно внутренних адресов и обозначений ролей.
